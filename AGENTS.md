# Maintenance Contract: agent-temp

This file is for agents editing the skill. Keep maintainer rules here, not in `SKILL.md`.

## File roles

| File | Role |
| --- | --- |
| `SKILL.md` | Trigger, root, commands, per-harness placement, rules |
| `scripts/agent-temp.mjs` | The only executable. Prunes the root, creates per-task folders, and removes one temp file or folder, or empties a scratchpad |
| `package.json` | Exposes the script as the `agent-temp` bin and keeps its version equal to `metadata.version` |
| `README.md` | Human skim layer. Keep it to a few lines |

## Contract of the script

- The prune unit is an entry directly under the root. A `claude` or `claude-<uid>` folder is never a unit, because Claude Code appends that folder beneath its temp override. Its project folders are not units either. Each session folder in a project is, so an old session's scratchpad goes while newer sessions keep the project in use, since no agent empties a scratchpad when its task ends. A loose file in either folder is a unit too. Inside it, `bundled-skills` is never a unit either. Claude Code keeps one folder per version there, and each version folder is a unit judged by age alone.
- Every old unit that is a folder, except a `bundled-skills` version folder, is checked for Git work before it goes. The scan walks the whole unit without following links and finds two kinds of thing: checkouts, which are folders holding a `.git` entry, and Git folders, which hold `objects` and either `HEAD` or `refs` (a checkout's `.git`, a bare repository, a submodule's store under `.git/modules`, a separate Git folder). The scan requires only one of `HEAD` and `refs`, so a damaged Git folder is still found. Names are matched without case on Windows and macOS, as Git matches them there.
- A checkout is kept when it has uncommitted changes, untracked files that are not ignored, a file marked assume-unchanged, or a file marked skip-worktree that is present, a dangling link included (a sparse checkout's absent files are fine). A linked worktree is also kept for commits not on any remote-tracking branch reachable from its HEAD or from the refs that belong to it alone (`refs/worktree`, `refs/bisect`, `refs/rewritten`), and, when its repository is outside the unit, for being locked.
- A Git folder is kept when it has a stash, no remote, commits on any ref not on a remote-tracking branch, or a linked worktree outside the unit. A non-bare Git folder is kept unless it is the Git folder of a checkout found in the unit, because its working tree was not inspected. That includes the store of a deinitialized submodule, whose files cannot be told apart from an unrelated repository kept in the same place.
- The unit is also kept when part of it cannot be read or any Git call fails or runs past its timeout. Nothing is deleted on a doubt.
- A checkout or Git folder whose own config (local or worktree scope) sets a `filter.<name>.clean` or `process` command is kept after a `git config` read and nothing else, because inspecting it would run that command. Git runs with no inherited `GIT_` variables, with `GIT_CEILING_DIRECTORIES` at the parent of the folder it inspects, with no transport allowed (`GIT_ALLOW_PROTOCOL`), lazy fetching off (`GIT_NO_LAZY_FETCH`), fsmonitor and signature display off, and optional locks off. Stashes are read as a ref, not through `git stash list`. So an inspection runs no command the repository supplies, reaches no remote, and writes nothing that the age check reads.
- After deleting a linked worktree whose main repository still exists, the script runs `git worktree prune` in that repository and reports the entry as stale if it is still there.
- Age is the newest modified time among the files inside a unit, so a folder in use is never judged by its own timestamp. A unit with no files is judged by its own modified time. A link counts as its own entry and is never followed.
- The root itself is never deleted. The script refuses a drive root, the home folder or an ancestor of it, the OS temp folder or an ancestor of it (named from fixed locations, since a harness may point its temp variable at the root), a folder that contains the current temp folder, and on Windows a UNC or extended-length path or a POSIX-style drive path. A root that is a link, or sits behind one, is resolved and every check runs on where it leads. A root equal to the current temp folder is allowed, since a harness may point its temp variable at the root.
- Per-task folders are named `<harness>-<label>-<6 hex>`. The harness prefix says whose folder it is when someone inspects the root, the label says what it was for, and the random suffix keeps parallel tasks from colliding. No timestamp is encoded, since the modified time already carries it.
- `clean` acts on exactly one path, never a pattern. It resolves the path and accepts three kinds. A scratchpad at `<root>/claude[-<uid>]/<project>/<session>/scratchpad` is emptied and left, because the harness made it. A file or folder inside a scratchpad is deleted. A file or folder directly under the root, or at any depth inside a folder there, is deleted, except the `claude` or `claude-<uid>` folder and what it holds. A file with one of those names directly under the root is a loose entry, as prune treats it. It refuses with exit 2 and the reason: an empty path, the root, the `claude` or `claude-<uid>` folder and any other path inside it outside a scratchpad, a link or junction as the path itself, a path whose real location is outside the root, a missing path, anything that is neither a file nor a folder, and a folder holding the current folder, except a scratchpad that is itself the current folder, since a process cannot delete the folder it runs in everywhere. A link above the path is followed, and only where it leads is judged. Flags only `prune` or `new` use are refused rather than ignored.
- `clean` runs the same Git check as prune on a folder or scratchpad, reusing its functions rather than a copy. A file holds no Git work of its own, so it skips that scan. A path inside a unit (a folder directly under the root, or a scratchpad) is kept with exit 3 when the scan finds any checkout or Git folder anywhere in that unit, since Git work beside the path can own it (a Git folder whose `core.worktree` is the path) or depend on it (a clone borrowing its objects through alternates). That is why `SKILL.md` sends an agent's own clones and worktrees to a task folder of their own, apart from scratch files, secrets, and locks. Ownership that crosses units, such as a `core.worktree` or alternates entry pointing into another folder under the root, is not detected by prune or `clean`. Because the scan looks only down, it also keeps the path when any folder above it, up to and including the root, holds a `.git` entry or is a Git folder by the same test the scan uses. When it keeps the path, it deletes nothing, names the checkout or Git folder and the reason, and exits 3. Ignored files never block it. `--dry-run` runs every check and changes nothing.
- `clean` then renames the path to a tombstone named `.agent-temp-deleting-<6 hex>` beside it, or moves every entry of a scratchpad into a tombstone folder of that name inside it, and deletes the tombstone. On Windows, a file another program holds open, which would make a delete fail partway and could leave a checkout too broken to inspect again, makes the move fail first, so `clean` puts back what it moved and exits 3 with nothing changed. Other systems allow the move, so this guards only that case. A delete that still fails after the move exits 1 and names the tombstone, which stays an ordinary entry under the Git check, so a name alone never bypasses it. Stale worktree entries are cleared only after a full delete, as prune does. `--dry-run` stops before the move, so it does not test for open files.
- `SKILL.md` routes every removal under the root through `clean` and forbids shell deletes there. It does not have an agent remove its task folder or scratchpad when the task ends: what is left stays for the user or a later agent to inspect, and the 30-day prune removes it. It allows only removals that must happen before then, such as a used credential or the agent's own lock, has the agent change files inside its own clone with Git or the project's own tools, and sends a lock or slot another tool hands out back through that tool. The reason sits in the Claude Code paragraph: Claude Code asks the user to approve some shell deletes even in bypass mode, so a shell delete can hold a task. It is stated as a cost to the user, never as a way around approval. The shapes named there are ones a headless Claude Code run denied, or that Claude Code's documentation lists as denied, while the same commands with `clean` in place of the `rm` ran. Recheck them against Claude Code's current documentation before changing that text.
- The script cannot tell which task or session a folder belongs to, so nothing in it or in `SKILL.md` may claim that it does. `SKILL.md` tells the agent to run `clean` only on its own files and folders, and never on a Claude Code scratchpad as a whole, since its subagents share it.
- Folder names the script matches (`claude`, `claude-<uid>`, `bundled-skills`, `scratchpad`) are matched without case on Windows and macOS, like Git's own names.
- Prune runs on use. There is no scheduled task.
- Default root, age limit, and Git timeout live in the script's constants. Change the root and age limit there and in the `SKILL.md` table and prose in the same edit.

## Editing rules

- Keep every frontmatter string quoted.
- Name harnesses in `SKILL.md` only in the placement table and the Claude Code paragraph beneath it, and only ones with a distinct way of getting scratch space. Beyond the Claude Code folder exception and its `CLAUDE_CODE_TMPDIR` setting, no rule depends on one particular harness.
- The skill says where temp goes and when it is removed, and temp is removed only through the script, never with a shell delete. Workflow choices such as whether to clone or push, or where secrets are stored, stay out of it.
- Keep the skill generic: no real project names, local paths, or dates.
- No em dashes, and no semicolons joining sentences.
- Bump `metadata.version` and `package.json` together.

## Before finishing

- Run skill-forge's validator (`node <skill-forge-root>/scripts/validate.mjs <skill-root>`) on a copy of the skill whose directory is named `agent-temp`, so the warning about repository checkout names does not apply.
- Run the script against a throwaway root holding an old folder, a fresh folder, a folder with an old directory but a new file, an old link pointing outside the root, a loose old file, and a `claude` folder holding a project with an old and a fresh session and a `bundled-skills` folder with old and fresh versions. Only the old units go, the project folder and the `bundled-skills` folder themselves stay, and nothing outside the root is touched.
- In the same kind of root, age these to past the limit and run `prune --dry-run`: a dirty clone, a clone with untracked files, a clone with a stash, a clone with an unpushed commit, a repository with no remote, a clean pushed clone, a linked worktree of an outside repository with and without changes, and a checkout whose `.git` points nowhere. Only the clean pushed clone and the clean worktree are listed. A real run then clears the deleted worktree's entry from its main repository. Then add a bare repository, a separate Git folder whose checkout is outside, a deinitialized submodule, files marked assume-unchanged and skip-worktree, a `.GIT` spelled in capitals, a worktree-local ref, a locked worktree, and a partial clone. Each of those is kept. A clean sparse checkout is listed for deletion. A dry run changes no file in the root.
- Run `clean` in the same kind of root. A task folder is deleted, and one holding a link to a folder outside the root loses the link but not the folder it led to. A scratchpad is emptied and stays. A file and a folder inside a task folder, a file and a folder inside a scratchpad, and a loose file directly under the root are each deleted and nothing beside them changes. A path inside a clone in a task folder, and one inside a bare repository there, is kept with exit 3. So is a file beside a clean pushed clone in the same task folder, a working tree whose Git folder sits beside it with `core.worktree` pointing at it, and a repository that a sibling clone made with `--shared` borrows objects from. Each of these is refused with exit 2 and nothing changes: the root, the `claude` folder, a project folder and a session folder inside it, the session's `tasks` folder and a file in it, `bundled-skills` and a version folder in it, a path outside the root, a junction or link under the root that leads outside it, a missing path, a POSIX-style drive path on Windows, and a folder holding the current folder. Each Git fixture that prune keeps blocks `clean` too, with exit 3, in a task folder and in a scratchpad, and nothing is deleted. A scratchpad whose session folder is a checkout with changes is kept with exit 3, and so is a task folder when the root is a checkout. On Windows, a task folder and a scratchpad holding a file another program has open are kept with exit 3 and nothing changed, and are cleaned once the file is closed. An empty path, a second path, and a flag `clean` does not use are refused with exit 2. A clean pushed clone whose only other file is an ignored `.env.local` is deleted. A clean linked worktree of an outside repository is deleted and its entry cleared. `--dry-run` changes nothing. Then break each guard in a copy of the script and confirm a test fails.
